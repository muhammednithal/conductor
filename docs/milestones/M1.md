# Milestone 1 — Single-Worker Linear Job Execution

## Goal
Stand up a minimal end-to-end pipeline: one Orchestrator service, one Worker, and Postgres. Execute linear DAGs (no branching) with durable state and gRPC communication between orchestrator and worker.

## Scope
- Orchestrator service: DAG parsing, step scheduling, state persistence via `statemachine` package
- Worker service: gRPC registration, task streaming, heartbeat, step execution for `http`, `transform`, and `delay` step types
- Linear DAGs only (all steps are in a single sequential chain; no `depends_on` branching)
- Postgres schema: `users`, `workflows`, `workflow_runs`, `step_executions`, `workers`, `leases` tables
- gRPC bidirectional streaming between orchestrator and worker
- Basic Redis task queue (`conductor:tasks` list)

## Non-Goals
- DAG branching or fan-out
- AI step types (`summarize`, `embed`, `rag`)
- Web dashboard
- Retry with exponential backoff (basic retry only)
- Crash recovery on orchestrator restart

## Acceptance Criteria
1. A 3-step linear workflow (step A → step B → step C) completes end-to-end with all steps in `SUCCEEDED` state in Postgres
2. Worker registers via gRPC and appears in the `workers` table with `ONLINE` status
3. Step state transitions are persisted to Postgres through the `statemachine` package (no direct SQL updates to `step_executions.status`)
4. `make test` passes in both `/orchestrator` and `/worker`
5. `make lint` passes in both `/orchestrator` and `/worker`
